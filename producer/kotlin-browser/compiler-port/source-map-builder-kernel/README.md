# Genuine source-map builder kernel

This independent recipe retains the complete `SourceMap3Builder.kt` and all three methods of `SourceMapMappingConsumer.java` from Kotlin commit `4d78aae1e337cd40f69baa865aed950fe807a775`. It prepares the original builder with explicit, pin-checked source spans and the complete Java interface as common Kotlin. VLQ encoding, Int overflow, name/source ordering, first source supplier, ignored sets, duplicate suppression, decreasing/equal column rewind and source-root calculation remain intact.

`SourceMap3Builder(generatedFileName, getCurrentOutputColumn, pathPrefix, host)` takes an explicit optional generated filename instead of a native `File` and a required `SourceMapBuilderHost(separatorChar, diagnostics)`. `SourceMapEmbeddingDiagnostics` has two required operations: `println(message)` followed by `reportThrowable(failure)` on a caught embedding IO failure. The caller supplies actual destinations and throwable rendering. There is no default destination, global registry or silent sink; the builder does not close diagnostics. Caller integration is separate, and native global `System.err` changes or full native stacktrace text are not claimed equivalent.

Source suppliers return the existing genuine `AstSourceReader`. The selected Kotlin/JVM `Reader.copyTo/readText` loop uses an 8192-character buffer, including zero reads and termination on a negative count. Its separate binding preserves the loop rather than using the AST reader's other 1024-character consumer. Kotlin nullable `Reader.use` closes once and keeps a read failure primary with later close failures suppressed, including the Kotlin self-suppression identity guard. Only `SourceMapIoFailure` and the existing `AstReaderClosedException` are classified as IO; other `Exception` objects are rethrown unchanged and `Error` bypasses the IO catch. Diagnostic exceptions occur after the catch and are not swallowed by the builder.

The genuine fastutil getInt/put/default -1 value-index operations bind to an actual common map. File identities must have stable `equals`/`hashCode` while in the builder. Equal, distinct and colliding keys are covered without claiming equality of arbitrary effectful hash evaluation counts, map capacities or internal representation.

`prepareSourceMapBuilder({sourceRoot, outputRoot})` and `verifySourceMapBuilder` return three common sources, the two replaced originals and canonical shared dependency pins. Existing AST, JSON, text IO, UTF8, byte sink, SmartList and assertion sources are reused once by their genuine owning components. Preparation is not execution evidence: its differential/caller/full-compiler flags remain false.

The observer rebuilds the whole original interface and builder against pinned genuine fastutil classes extracted only from the official bootstrap artifact, with only the oracle import relocation changed. Its runtime uses the previously verified rebuilt original AST and excludes bootstrap compiler models. Common JVM and Wasm compile the actual full 113-source AST and shared helpers; Node and an offline Chromium module worker execute the same module. Native `Reader.use`, buffer size and self-suppression dispatch are checked in the pinned stdlib bytecode. The finite profile covers stateful seeded mappings, signed endpoints, rewind, repeated build/supplier calls, nullable readers, read/close `Exception` and `Error`, diagnostic ordering, throwable identity and real byte effects. Controlled JVM `IOException.printStackTrace` overrides observe the explicit reporter protocol; raw standard closed-reader/native-stack output remains separate and unnormalized.

The final profile has **1,334 exact selected value/effect and failure-category records** across all four hosts, **11 completed commands**, **133 genuine fastutil support classes** and **18 passing integrity guards**. Collision growth through 129 distinct equal-hash identities, equal-key first-supplier winners, failures after partial reads, and a reused native string reader are included. The two raw closed-reader reports per host retain standard JVM trace text and common diagnostic text rather than claiming those rendering boundaries match. Chromium 153 runs the module worker offline after initialization with no external/offline requests or page errors. The earlier 1,312-record positive profile and its exact input snapshot remain pinned separately.

The original algorithms allocate ordered sources/names, mapping text, JSON and embedded source text without a new arbitrary limit. Lookup is expected constant time with ordinary stable hashes and can degrade with collisions. A supplier can perform unbounded work or repeatedly return zero; the original read loop is retained, and this finite corpus does not claim whole-compiler resource acceptance, arbitrary JVM Reader subclass dispatch or maximum allocation behavior. The explicit separator profile is tested against the real POSIX JVM oracle; native Windows filesystem behavior is outside this unit.

Path resolver/consumer binding, real incoming compiler callers, full JS parser and complete compiler acceptance are outside this kernel. No methods or phases are dropped; all readiness flags remain false.
